# 基类 · 品味

> **什么时候读它**：要做**界面 / 文案 / 命名 / 排版 / 规则本身**的判断时。
> **它不是"必须遵守的规则"**，是"这类判断通常涉及哪些方面"的参考物。
> 看了不适用就删，用了发现是坑就补进易错点。
>
> ⚠️ **下面各领域表里写的「禁忌」，是"通常会成为禁忌"，不是母版强制。**
> 它和作业格式要求那种硬性规定不同——**要不要执行，由项目自己定**。
> 母版只提供"这类判断通常有哪些维度"，不替你拍板。
>
> **本文件只放"去掉某个项目名还成立"的内容。**
> 具体色板、阈值、组件清单归**项目自己**，不归这里（见 `..\母版立场.md`）。

---

## 一、它解决什么

**不是"教 AI 审美"，是把品味从「评分」改成「筛选」。**

因为给 AI 打分（"简洁 0.3 / 精致 0.4"）会产生**均匀**，而均匀正是"AI 味"本身。

---

## 二、三个论断

### ① 审美里有一半其实是物理

"丝滑""稳""松""抢眼"——**能被翻译成毫秒、曲线、网格、对比度**。

| 人的说法 | 物理量 |
|---|---|
| 丝滑 | 过渡 150–250ms、`ease-out`、只动 `transform`/`opacity`、无 delay |
| 稳 | `cubic-bezier(.4,0,.2,1)`、250ms |
| 松 | 间距档整体上调一级、行高 1.7 |
| 克制 | 强调色同屏只出现 1 处 |
| 抢眼 | **字号跳 2 级**（不是 +1px） |

> **人的"丝滑"是一段被压缩的感官经验；AI 的"丝滑"是一个词的文本邻居的中心。**
> **差别不在知不知道，在锚定在什么上。**

### ② "AI 味"的本质是**均匀**

| AI 味 | 人味 |
|---|---|
| 所有元素同等重要 | 有明确的轻重 |
| 所有句子同等加粗 | 只有一句值得加粗 |
| 所有函数同等抽象层级 | 有的深、有的浅 |
| 所有条款同等强制 | 有的不许改、有的随便改 |

**共同点：AI 不敢"偏"，因为它没有偏好。没有偏好，是因为没有意图。**

### ③ **意图只能人给**

**AI 从不问"这一页 / 这段 / 这个函数唯一重要的是什么"。**

> **尺度规则保证"不乱"，但"不乱"≠"好"。**
> **"好"来自"有轻重"，"有轻重"来自"有意图"。**

---

## 三、漏斗四层（**为什么不用权重**）

### 权重是下下策，四条理由

| # | 理由 |
|---|---|
| 1 | **审美不是可加的**——"克制"和"强调"互相定义，不能各自加分 |
| 2 | **权重抹掉"为什么"**——"简洁 0.3"不告诉 AI 什么时候该牺牲简洁 |
| 3 | **权重不可维护**——20 个旋钮调一个影响全部，且没有正确答案可验证 |
| 4 | **权重本身就是平均制造机**——加权求和必然趋向"每个都占一点"，**那正是 AI 味** |

### 人的"看重"，翻译过来永远不是权重

| 你说的 | 实际是 |
|---|---|
| "我更看重简洁" | **冲突时保简洁** → 优先级 |
| "这个绝对不能接受" | **一票否决** → 禁忌 |

> **权重只在"两者都没有强烈偏好"时真实存在——而那恰恰是最不需要审美的地方。**

### 四层

```
① 禁忌    出现即失败，不可协商
② 优先级  冲突时谁赢（是序列，不是数值）
③ 范例    像哪个 / 不像哪个（最近邻，不是评分）
④ 偏好    个人风格（人给，不做机制）
```

### 它和现有规则系统是同一套结构

| 漏斗层 | 母版已有的东西 |
|---|---|
| 禁忌 | **`01-核心规则` §〇 不变式** |
| 优先级 | **§1 规则来源分层** |
| 范例 | **更新日志**（为什么这么改 = 反例库） |
| 偏好 | **`02-模式.md`** |

> **品味不是新东西，是这套结构换了个领域用。**

## 四、分领域：只给禁忌表

**规则：这里只放"有外部标准或通用成立"的禁忌。**
**项目自己定的阈值归项目。**

### 界面

| 禁忌 | 依据 |
|---|---|
| 用 emoji 顶替图标 / 图片 / logo | 渲染不一致、无法控重、**一眼像没做完** |
| 正文对比度 < 4.5:1 | WCAG AA |
| `transition: all` | 会动画 layout 属性，必然掉帧 |
| 不写 `prefers-reduced-motion` | 无障碍 |
| 强调色同屏 > 1 处 | = 没有强调 |
| 中英数字混排不指定字体栈 | 会出现两种观感 |

### 代码

| 禁忌 | 依据 |
|---|---|
| 调试残留（`print` / `console.log`） | — |
| 占位实现（声称实现但只是近似，且没标注） | **已是母版不变式** |
| 魔法数字（无命名的阈值） | 改一次要全文搜 |
| 同一件事两种写法（项目内） | = 没有偏好 |

### 文档

**先确认读者是谁**：读者是 AI 的，只需「结构清晰、可检索」；读者是人的，才看排版。

| 禁忌 | 依据 |
|---|---|
| 加粗用太多（一段 > 1 处） | 加粗用太多 = 没有加粗 |
| 表格 > 4 列 | 眼睛横跳，读三行就丢 |
| 嵌套 > 2 层 | 第 3 层说明该拆文件 |
| 一节讲多件事 | 超过 ~12 行考虑拆 |

### 规则本身

| 禁忌 | 依据 |
|---|---|
| 重复（两条说同一件事） | `audit` 已在查 |
| 不可验证（写了但没法判定做没做） | = 等于没写 |
| 死条款（从建立至今没触发过） | 占硬预算 |
| 追不到真实失败 | 母版的规则应当"撞出来的，不是设计出来的" |

## 五、意图怎么写（**可验证，不是可形容**）

| ❌ 要求（形容词） | ✅ 意图（可验证） |
|---|---|
| 要丝滑 | 点加号后数字**立刻**变，且**察觉不到**过渡 |
| 要有层次 | 进来**第一眼**看 A，第二眼看 B |
| 要美观 | 同一屏里**强调色只出现在 1 个地方** |
| 要简洁 | 这段代码**删掉任意一行都会丢信息** |

**判据：**
> **意图应该能被"验证"，不能被"形容"。**
> **写不出可验证的意图 → 还没想清楚 → 先别交给 AI。**

---

## 六、范例层（母版最缺的那一层）

**现有系统全是"别做什么"（易错点 / 不变式 / 红线），没有"这就是对的"。**

```
<项目>\examples\
    good\    ← 这就是对的（3–5 个）
    bad\     ← 这就是错的（1–2 个）
```

**可验证的方式不是打分，是比对：**
> 新产出**像 good/ 里的，还是像 bad/ 里的？**

**"像不像"人一眼能判，不需要专业素养。**

> **范例要极简**——几行文字或一张小图就够。
> **初期可以完全没有**，靠反哺慢慢积累（见 `..\反哺流程.md`）。

---

## 七、它治不了什么

| 治得了 | 治不了 |
|---|---|
| 廉价感（占位资产、尺度混乱、无强调） | "这一版比那一版优雅" |
| 均匀（每处同等重要） | 留白节奏的高级感 |
| 可验证的下限 | 原创的语言 / 风格 |

**最后那一公里只能靠人。**
**而人的做法是"定调 + 给参照 + 挑方案"，不是"解释审美"。**

---

## 八、易错点

| 坑 | 教训 |
|---|---|
| 把品味写成权重表 | **权重会制造"均匀"，正是 AI 味的来源。用序列，不用数值。** |
| 把项目阈值抄进这个文件 | 换个项目就错。**判据：去掉项目名还成立吗？** |
| 写了禁忌但没有检查 | **等于没写**（和"规则放在文件里不等于会被执行"同一个病） |
| 把"要美观"当目标 | 形容词不可验证，AI 只能猜。**必须翻译成可判定的** |
