# 基类 · 代码

> **参考物。** 用于任何要动代码的工作区。抄走适用的，删掉不适用的。
> 最后更新：2026-10-14

---

## 一、通常涉及哪些方面（**先看这节，对照检查有没有漏**）

### 1. 环境与依赖
- 用什么语言 / 版本？跑在哪（本机 / 容器 / 服务器）？
- 现有哪些依赖？**能不能加新依赖**（还是只能用标准库）？
- 有没有虚拟环境 / 锁定文件（`requirements.txt`、`package-lock.json`）？
- 别人拿到这个项目**怎么跑起来**？（README 里有没有这一步）

### 2. 目录与命名
- 代码放哪？测试放哪？配置放哪？产出/日志放哪？
- 命名风格（驼峰 / 下划线）、文件命名有没有既定习惯？

### 3. 代码边界
- **哪些是核心逻辑、哪些是边角？** 核心逻辑改动要更谨慎
- 有没有"不该动"的文件（自动生成的、第三方的、别人负责的）？
- 改动范围：只改指定文件，还是允许连带调整？

### 4. 运行与验证
- **怎么知道改对了？** 有没有测试？没有测试的话怎么验证？
- 有没有可以一键跑的自检脚本？
- 改动会不会影响已有数据 / 已有结果？

### 5. 错误与日志
- 出错时怎么表现（抛异常 / 返回错误码 / 静默）？
- 关键路径要不要打日志？日志写哪、什么级别？

### 6. 版本与回滚
- 用 git 吗？还是靠复制备份？
- **改坏了怎么退回去？** 修改前要不要先备份？

### 7. 交付形态
- 最终要交什么：源码 / 可执行文件 / 演示 / 部署好的服务？
- 有没有性能、体积、兼容性上的硬要求？

## 二、默认约束（挑适用的抄进工作区规则）

- **写前先读**：改任何文件前先完整读它，不凭记忆或猜测动手。
- **只改该改的**：不顺手重构、不调整无关代码的格式、不批量重命名。
- **加依赖先问**：引入任何新库 / 新框架前必须报告并等确认。
- **不删代码**：要废弃就注释或标 `[已作废]`，保留可回溯。
- **改完自证**：说明"怎么验证的、结果是什么"，不能只说"应该可以了"。
- **异常结果先查原因**：结果为 0、多组数据完全相同、程序没报错但没输出 → 先定位，不当作正常。
- **关键改动前备份**：至少记下改动前的文件内容或留一份副本。

## 三、易错点（攒出来的，空着正常）

| # | 坑 | 规避 |
|---|---|---|
| 1 | **为想象出来的场景写代码**（详见下方） | 动手前先问：**这个机制在"当前有几个人、几台机器在用"的条件下，回报是正的吗？** |

### 关于第 1 条：为想象的场景写代码

**症状**：写了一个"设计上应该完备"的机制，但它在当前条件下**从来不触发**，
或者**触发了也只是制造噪音**。

**判据（动手前问两句）**：

1. **这个场景现在真的存在吗？**（不是"将来可能需要"）
2. **它现在会跑吗？跑了有正回报吗？**

**两次实测（2026-10-15）**：

| 我做的 | 我以为的问题 | 实际 |
|---|---|---|
| 加 `git fetch` 检查母版新版本 | "看不到远程新版本" | 母版就在本地、**根本没配 remote**。fetch 永不生效，失败时还报红 |
| 给"复制是快照"造更新机制 | "副本跟不上母版" | 当时**只有 1 个工作区**，手翻日志比跑脚本快 |

**共同点**：**都成立的前提是"多机 / 多人 / 多工作区"，而当时都不是。**

**更值得警惕的是**：这两次都是**在别人的报告上直接动手**，没有先质疑前提。
别人说"这是缺口"，我就认了。

> **所以配套一条**：**收到"这里有问题"的报告时，先验证那个问题成立的前提，
> 再决定要不要动手。** 报告者的前提可能是错的——哪怕报告者也是 AI。

## 四、可选强化（项目重要时加）

- **`[H]`/`[A]` 分级**：把"人必须自己写"的核心逻辑标 `[H]`，AI 只做提示和审查；其余标 `[A]`。
  适合：学习场景、核心逻辑不能出错、需要人真正掌握。
- **接口冻结 + 变更请求**：接口定稿后标 `FROZEN`，改动必须先提变更申请。
  适合：多角色协作、接口被多方依赖。
- **度量台账**：记录每个任务的耗时、返工次数、缺陷数。适合：需要写过程报告的场景。
