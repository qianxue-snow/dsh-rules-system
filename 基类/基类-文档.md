# 基类 · 文档

> **参考物。** 用于产出物主要是文字的工作区（报告、论文、周报、技术文档、综述）。
> 最后更新：2026-10-14

---

## 一、通常涉及哪些方面（**先看这节，对照检查有没有漏**）

### 1. 读者与用途
- **谁看**：老师 / 评委 / 同事 / 自己？
- **看完要做什么**：评分 / 决策 / 照着做 / 存档？
- 读者**已经知道什么**、**不需要知道什么**？（决定背景要写多少）

### 2. 体裁与硬格式
- 是论文、报告、周报、说明书还是综述？各体裁结构完全不同。
- **有没有格式文件？** 有就必须先读它，不能凭记忆。
  （课程作业尤其如此：章节数、每部分叫什么、字数、模板样式，**每次都要按当次的文件来**）
- 有没有页数 / 字数上下限？

### 3. 结构
- **先写目录再写正文**，不要边写边想结构。
- 章节之间有没有既定顺序（比如实验报告：目的→方法→结果→讨论）？
- 哪些章节是必须有的、哪些可以合并？

### 4. 素材与来源
- 写作依据是什么：实测数据 / 参考文献 / 现有文档 / 会议记录？
- **每个数字、每个结论的出处记下来**，写到后面会忘。
- 参考文献格式（GB/T 7714？APA？）有没有要求？

### 5. 内容边界
- **明确不写什么** —— 跑题是最常见的失分点。
- 哪些内容属于"内部过程"（不该出现在交付文档里）？
- 要不要写局限性与不足？

### 6. 数据与事实的呈现
- 数字标来源；图表要有编号和标题。
- **区分【事实】/【推断】/【待验证】**，不要把推测写成结论。
- 引用的内容必须标出处，禁止凭印象编造参考文献。

### 7. 交付与归档
- 交付格式：`.md` / `.docx` / `.pdf`？
- 文件命名规则（常含学号、姓名、周次、版本）？
- 放哪、要不要同时留一份源文件？

## 二、默认约束（挑适用的抄进工作区规则）

- **先读格式要求**，再动笔。格式文件是需求来源，不是参考。
- **先出目录/大纲**，确认结构后再写正文。
- **不编造**：数据、引用、事实必须有出处；查不到就写"未找到"，不写"通常认为"。
- **区分三类信息**（事实 / 推断 / 待验证），逐条可追溯。
- **写完自检**：结构是否完整、格式是否合规、数字是否与来源一致、有没有残留占位符。
- **不改历史交付物**：已提交的版本不回改，要改就出新版本。
- **一次一章**，写完一章就停下来核对，不要一口气生成全文。

## 三、易错点（攒出来的，空着正常）

| # | 坑 | 规避 |
|---|---|---|
| 1 | 把"预期/示例"数据当成实测结果写进去 | 每个数字标来源；示例必须显式标注"示例" |
| 2 | 凭记忆套用上次的格式要求 | **每次重新读当次的格式文件**，格式会变 |
| 3 | 结构写歪 → 全部重写 | 先出大纲并确认 |
| 4 | 引用编号与实际文献不对应 | 写完统一核对一遍编号 |
| 5 | **用 Word 打开 .docx 来验证生成成功** | **禁止。** 详见下方「验证纪律」 |
| 6 | 用 **PowerShell 双引号插值**拼 Markdown 再写文件：反引号 + `0`/`a`/`f`/`r` 会被当成转义，写出 NUL / BEL / 换页 / 回车，之后整个文件被判成"二进制"、改不动 | 写正文**别经双引号插值**：用单引号 here-string（`@'…'@`）或直接按 UTF8 写。出现 "binary file" 先扫控制字节（`[IO.File]::ReadAllBytes`），别以为文件坏了 |

## 四、验证纪律（**实测换来的**）

### 铁律：能证明同一件事时，永远选便宜的那个

**问自己：我要证明的是什么？**

| 要证明的 | 正确做法 | 耗时 |
|---|---|---|
| 文件生成成功、结构合法 | 读文件头 / 解 zip / 解析 XML | **毫秒** |
| 内容正确、没丢字 | 解析内容，与源文件比对 | **秒** |
| 渲染效果、排版好看 | 才需要真的打开看 | **分钟** |

> **实测（2026-10-15）**：一个会话为验证 4 份 .docx，**四次启动 Microsoft Word**
> （每次 `Start-Sleep 22` 秒后看标题栏），另加一次 COM 调用 Word **卡死 120 秒**，
> 合计约 **4 分钟**——只为了证明"文件能被打开"。
>
> 而等效的结构验证脚本跑完 **181 毫秒**，而且查得更严（字数逐字比对、OOXML 子元素顺序）。
> **更糟的是那次 Word 显示的是「受保护的视图」，脚本却判定通过——这个手段本身就不可靠。**

### 具体到 .docx：用现成工具，别自己发明验证方式

```
规则系统\基类\工具\md2docx.py      转换（零依赖，不开 Word）
规则系统\基类\工具\verify_docx.py  验证（毫秒级，查结构+内容+OOXML 规范性）
```

**禁止**为了让"文件能打开"而启动 Word / Excel / PowerPoint 等 Office 程序做验证——
它们的启动成本（20 秒起）远高于它提供的保证。

### 验证时机

写完**一起验**，不要每产出一份就验一次。线性重复是最容易避免的浪费。

## 五、可选强化（项目重要时加）

- **需求编号化**：给每条需求编号（R-01、R-02…），正文与验收都引用编号。
  适合：有明确验收标准的正式交付。
- **产出物固定段模板**：规定交付文档必须包含哪几节（如：产出摘要 / 清单 / 决策与依据 / 偏差说明 / 待人工验证项）。
  适合：多任务流水线，保证每份产出结构一致。
- **需求↔任务↔成果追溯矩阵**：一张表把三者对齐。
  适合：要证明"每条需求都做了"的场合。
