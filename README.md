# 规则系统

> 建立：2026-10-14
> 解决什么：**每次开工的准备阶段太长太繁琐，而且人自己也会漏东西。**
> 不是什么：不是又一套工作流规范。是**一套让"定规则"这件事变便宜、并且不会漏**的装置。
>
> ⚠️ **要决定"母版该怎么改"时，先读 [`母版立场.md`](母版立场.md)。**
> 下游有 `AGENTS.md` 说明它是谁，母版原本没有对应物——那一页就是补这个缺口。

---

## 第一次点进来？先看这五段

**这是什么**
一套给 AI 编码代理用的**工作区规则系统**。一个工作区 = 一个 `AGENTS.md` 入口 +
一份共享规则 + 一个状态文件。已经迭代了 30+ 个版本。

**为什么存在**
每次开新会话，都要重新交代"这个项目是什么、做到哪了、有什么规矩"——**准备工作吃掉了注意力**。
更麻烦的是：对话一长，AI 就忘了，产出不再更新，人开始失控。

**最值钱的不是规则，是 `更新日志.md`**
规则本身压缩到 170 行，看着很平淡。
**但每条规则都能追到一次真实失败**——"为什么这句话必须写"全在更新日志里。
想看设计思路，从那里读。

**它不解决什么**
- ❌ AI 的**品味**（只能用"漏斗 + 人挑"缓解，给不了）
- ❌ AI 的**判断力**（该不该做这件事，仍要人定）
- ❌ **语义正确**（工具只查结构，`audit` 绿了不等于内容对）

**怎么开始**

| 你想 | 读 |
|---|---|
| 知道它长什么样 | 本文 §三 目录结构 |
| 建一个新工作区 | [`00-准备流程.md`](00-准备流程.md)（照着勾，约 10 分钟） |
| 理解核心约束 | [`01-核心规则.md`](01-核心规则.md)（170 行，一次读完） |
| 看它为什么长这样 | [`更新日志.md`](更新日志.md)（**倒着读**，最新在上） |
| 改这套规则本身 | [`母版立场.md`](母版立场.md) + [`反哺流程.md`](反哺流程.md) |

**许可**：[MIT](LICENSE)。随便用、随便改。

## 零、权限边界（**最重要的一条，先看这个**）

**本目录是母版。它只由"宿主工作区"（`dsh_杂活`）维护。**

| 谁 | 能做什么 |
|---|---|
| **宿主工作区**（`dsh_杂活`） | ✅ 改本目录任何东西、提交 git、打 tag、发版 |
| **任何下游工作区** | ❌ **对本目录只读。一个字都不改** |

**下游工作区发现母版有缺陷怎么办？**

> **记一笔，然后由人转达给宿主工作区。**
> **不要自己动手改，也不要在自己的对话里展开讨论怎么改。**

**为什么这条要单独列出来**：下游工作区越界改母版，等于**在没有全局视野的情况下改公共资产**——
它不知道别的谁在用、改了会影响什么。**这类事只能有一个地方做。**

> **推论**：下游工作区的对话里**不应该出现**"怎么改母版""怎么提交 git""怎么修母版漏洞"
> 这类话题。**它们是维护行为，不是使用行为。** 混在一起就是噪音。

## 一、它要解决什么

**一句话**：**把"准备工作"的成本压到最低，让它不再吃掉你的注意力。**

| # | 什么时候 | 痛在哪 | 对策 |
|---|---|---|---|
| 1 | **开工** | 每开新工作区都要重新讲一遍规则、指定约束 | `骨架\` 整个复制，只填空不重建 |
| 2 | **开工** | 每次都要靠人提醒 AI"去看规则" | 根 `AGENTS.md` 自动注入，**不用嘱咐** |
| 3 | **过程中** | **对话一长就忘，产出不更新，长项目失控** | **收尾判定标准 + 状态文件 + 开工回执** |
| 4 | **交付 / 学习** | 产出"看起来做完了"；学习型项目翻回去看，不知道自己长了多少本事 | **交付物 5 段 + 禁止占位实现 + 人类练习反馈** |

> **第 3、4 条才是这套系统的价值所在。**
> 前两条只是让你少说几句话；**后两条决定的是一次长项目会不会失控。**

### 它的血统（别丢掉这段）

这套东西不是凭空设计的。内核来自 **2026-10-12 在 `科教` 项目上打的两次补丁**：

- **`5.1` 每轮收尾必须更新任务看板**（强制）——因为"新会话要恢复上下文，靠的就是任务看板，
  没有机制能自动知道上次做到哪"
- **`9` 每轮启动检查行**（强制）——因为"**规则放在文件里不等于会被执行**"

**那两条补丁，就是为了治"对话一长就失控"。** 后来把它泛化成可复用的系统时，
**这两条的内核必须留着**（现在的对应：§6 收尾纪律、§3 开工回执）。

## 二、三条设计原则

### 原则 1 · 分开"必读"和"参考"

```
01-核心规则.md    必须遵守 —— 每轮都进上下文，所以必须极短
基类\*.md         可以选择 —— 只在准备阶段翻，不进每轮上下文
```

**核心规则是"法律"，基类是"词典"。** 词典可以很厚，法律不行。

### 原则 2 · 基类是参照，不是命令

基类记录的是"**这类工作通常涉及哪些方面**"，不是"你必须这样做"。

- 看了不适用 → 当场删掉，不要硬套
- 用了发现是坑 → 补进该基类的「易错点」一节
- **它的价值在于把"你没想到要考虑 X"变成"清单上有 X"**

### 原则 3 · 积累要分两道，不是一道

新经验**不直接进核心规则**，先躺基类：

```
运行中发现某条约束有用
      ↓
写进 基类\<领域>.md 的「易错点」        ← 便宜，随时加
      ↓
同一类坑踩到第 2～3 次
      ↓
升级进 01-核心规则.md                  ← 贵，要慎重
```

**为什么**：核心规则每轮都进上下文，有硬预算（65,536 字节）。
没验证过的经验不该占每轮成本。**冗杂只发生在核心层，而核心层有闸门。**

```

├─ 版本.txt                  ← 【每次发版覆盖】一行版本号——下游靠它判断有没有更新

├─ 待更新\                    ← 【每次发版新增一份】vX.Y.md = 给下游的变更清单
├─ 更新日志.md                ← 【每次改这里记一条】完整历史，它比清单厚得多

├─ 对话测试.md                ← 【母版专有】T1–T10 手动探针（**别给被测会话看**）
├─ 基类\                     ← 【参考区】
│   ├─ _清单.md             ← 一行一个基类：名字 + 什么时候该翻
│   ├─ 基类-代码.md

│   ├─ 基类-Unity.md
│   ├─ 基类-实验.md

├─ 骨架\                     ← 【可整个复制】新工作区的空壳
│   ├─ README.md            ← 每个文件复制到哪（两类去向不同，别搞混）
```

## 四、怎么用（最短路径）

| 你要做什么 | 怎么做 |
|---|---|
| **开新工作区** | 打开 `00-准备流程.md`，从上往下勾。约 10 分钟 |
| **已有工作区** | 什么都不用做。根 `AGENTS.md` 已经自动生效 |
| **干一个活** | 直接说。AI 会先自查规则完不完善、有没有更新，然后交回执再动手 |
| **怕它忘** | 看 `任务看板.md` 的「当前该做的事」。**收尾有没有做到位，就看这一节** |
| **要交付了** | 提醒它按「交付物 5 段」写。**第 5 段「人类练习反馈」要你自己填** |
| **踩到新坑** | 写进 `基类\<相关>.md` 的「易错点」。**不要直接改核心规则** |
| **AI 说"做完了"** | 先问一句："**一个全新会话只读状态文件，能说出下一步吗？**" |

### 三个最容易被忽略的动作

1. **交接前先看状态文件** —— 判断收尾有没有做到位，只看这一件事
2. **学习型项目里，第 5 段必须自己写** —— AI 代填就等于没有
3. **它说"实现了"时，问一句"是真的还是近似"** —— 这是「禁止占位实现」要防的

## 六、本系统自身的维护

> **这一节是"维护这套规则"时看的，干活不用读。**
> **日常只需要记住一句**：改了母版规则 → 新建 `待更新\vX.Y.md` + 覆盖 `版本.txt`（漏了就等于"发了版但没通知"）。
> 详细流程在 `更新机制.md`。

### 改了母版，已有工作区会怎样

**不会自动同步** —— 它是复制，不是链接。但分工能绕开这个代价：

| 改什么 | 会不会同步到已有工作区 | 该怎么办 |
|---|---|---|
| `01-核心规则.md`、`02-模式.md`、`03-子代理.md`、`基类\*` | ✅ **会**（工作区里的 GLOBAL_WORKFLOW 引用它们） | 通用改进写这里 |
| `骨架\*` | ❌ 不会（已复制的副本是快照） | 只收"结构"层面的东西，结构很少变 |

**所以：通用性强的改进 → 写进核心规则或基类；骨架只改结构。**

### ⚠️ 加规则之前，先过两道闸

**这个系统最大的风险不是"规则不够"，是"规则越加越厚、互相打架、没人读完"。**
所以**新规则进核心之前必须回答两个问题**：

| # | 问题 | 答案的处理 |
|---|---|---|
| **1** | **已有哪条规则在管同一个问题？** | 有 → **改旧的，不新增**（在更新日志里写"改了 §X，因为…"） |
| **2** | **这条规则每轮都要读吗？** | 不 → **进 `基类\` 或工具文档**，不进 `01-核心规则.md` |

**判定"每轮都要读"的判据**：这条规则**很可能在这一轮就被违反或用到**吗？
- 是 → 核心（比如回执、授权边界、写操作纪律）
- 只在你**主动用某个工具/做某类验证**时才相关 → **基类**
- 只在**特定专业领域**才相关 → **基类-XX.md**

**并且把判断写进更新日志的条目里** —— 让"为什么新增而不是改旧的"留下痕迹，
下次翻日志时能看出当时的取舍。

### 定期自检：`工具\audit.ps1`

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File 基类\工具\audit.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File 基类\工具\audit.ps1 -SelfTest
```

**先跑 `-SelfTest`**（证明检查器自己没坏），再看结果。

它查这些——**全部机械可查，不靠人记**：

| 检查 | 抓什么 |
|---|---|
| **核心规则行数/字节** | **膨胀**（硬线 170 行 / 警示线 150） |
| 跨文件重复的规则句 | **冗杂**（同一句话说在多处） |
| 引用的文件是否存在 | **断链**（含"待建/举例/泛指"的排除规则，避免误报） |
| 核心规则里 `§x` 引用 | 引用了**不存在的节** |
| **下游工作区的回执格式** | **漂移**（母版加了字段，下游没跟） |
| 骨架占位符 | 提醒"这是模板，别当成品" |
| 必需文件是否都在 | 结构缺失 |

> **它查不出语义冲突**（两条规则在说反话）——**那只能靠人全文读**。
> 所以还要有下面这一步。

### 发版前：全文审一遍（**工具抓不到的那层**）

**只在发版时做，别每轮做。** 三个问题，扫一眼：

- [ ] 有没有**两条规则在说反话**？（例：「模式可选」vs「模式必填」）
- [ ] 有没有规则**没人引用**？（孤儿——当时为什么加，现在还需要吗）
- [ ] 有没有规则**从不触发**？（写成摆设，占着每轮的上下文）

> **实测（2026-10-18）**：一次全文审就抓出 6 处自相矛盾，其中最扎眼的一条是
> ——**核心规则开头写着「必须短」，而它自己已经 302 行。**
> **工具查了一百遍也查不出这个。**

### 这套维护机制的来历

**它不是设计出来的，是撞出来的。** 每一条都对应一次真实事故：

| 机制 | 因为什么加 |
|---|---|
| 更新日志 + 版本号 | 工作区多了之后不知道谁落后多少 |
| 母版只读 | 下游工作区开始"帮母版修漏洞" |
| 不变式 | 派生工作区把"必须有回执"这条元规则弄丢了 |
| 回执加 `【模式】` | 它挂在"可选"下面，**实测一次都没标** |
| 派活四必须 | 派了 9 个子代理，**只有 2 个交回执**——主模型没写进派活要求 |
| 内容 + 结构两类检查 | 替换锚点写窄，**旧内容 20 行留在原地**，而"记特征串"查不出 |
| 先校准尺子 | 两个工作区各自被自己的检查手段骗过（**至少 4 次**） |
| `audit.ps1` + 加规则前查重 | **核心规则 78 → 302 行**，其中 24% 是"按需"内容占着"每轮"的位置 |

> **一句话**：**这套系统靠"出事 → 加一条 → 定期收一收"运转，
> 不靠一开始就把规则想全。** 所以"收一收"这件事本身必须有机制——就是上面这几条。
